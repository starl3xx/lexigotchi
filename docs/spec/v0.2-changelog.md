## 2. Hard rule: one word, one NFT, case-as-state

This resolves the "who wins the jackpot if lowercase CRANE and UPPERCASE CRANE have different owners" question: **that situation is unrepresentable.**

- `Words.sol` mints at most one token per dictionary word for the word's lifetime: `tokenId = keccak256(word)`. A claim while that tokenId exists must revert.
- The Word NFT's case state is **derived from its escrowed letters**: 5 lowercase = `lowercase`; 5 uppercase = `UPPERCASE`; anything else = `Mixed`. Never stored independently — always computed or event-synced from escrow contents, so it cannot desynchronize.
- Upgrade rolls on escrowed letters mutate the escrow in place (burn lowercase 1155 ID, mint uppercase ID into the same escrow), transitioning the same NFT through `lowercase → Mixed → UPPERCASE`.
- Jackpot resolution is therefore a single lookup: does `keccak256(todaysAnswer)` exist, is it staked, is it not `hungry`? If all yes → pay its owner. Else → roll over. Case never affects jackpot resolution; it only affects daily yield.
- Dissolution (burn word, recover letters, free the name) is unchanged from v0.1; trophy history persists in the registry keyed by word, not by tokenId instance.

## 3. New feature — the Showcase (P1)

Players arrange **any letters they own** into **any string** (no dictionary check) and render it as the rubber-hose chorus line for sharing. This is the vanity/social surface — handles, GM, inside jokes — and the primary organic growth loop: every showcase cast is an ad.

- Input: 2–8 letters, A–Z only, drawn from the connected wallet's actual 1155 balances (a letter can be reused across showcases but each render reflects real ownership at render time).
- Output: image (OG-card format) + optional short animation, rendering each character with its **true case and states**. Compose-cast intent on Farcaster; downloadable/shareable image on web.
- **Strictly off-chain/read-only:** no minting, no staking, no escrow, no fee in v1. Showcases confer zero economic rights — they are not claims. The Lexidex and claim system remain dictionary-only.
- Build note: this is an indexer + render service feature (the same render pipeline as Word chorus lines, minus the stage/trophy chrome), not a contract feature. Schedule it accordingly.
- Why it matters economically: it creates letter demand *outside* dictionary demand (someone hunting an X to spell their handle), deepening the rare-letter market without consuming claims.

## 4. ETH auto-swap implementation notes

- Mint functions accept either $WORD directly or ETH; ETH path swaps to $WORD via an onchain router (Uniswap v3 / aggregator) inside the mint flow, with a frontend-supplied quote and slippage bound; revert on excessive slippage rather than absorbing it.
- All fee splits (§6 of v0.1) operate on the $WORD amount post-swap. Treasury never accumulates ETH from mints.
- Surface both prices in the UI ("0.001 ETH ≈ 420 $WORD") but treat $WORD as canonical.

## 5. Knock-on effects to verify in the build

1. **Rewards Pool outflow model:** with yield now UPPERCASE-only, early-phase distributions go to very few words. Keep the daily distribution as %-of-pool (it self-scales), but expect tiny early payouts — this is fine and intended; do not "top up."
2. **Pity counter scope:** per 1155 token *instance* is impossible (1155s are fungible within an ID) — track pity **per (owner, letterId) pair**, reset on success or on transfer of the owner's last token of that ID. Document this in `Rolls.sol`.
3. **Daily mint Sybil gate:** 1/day discounted mint keys on **FID** (Farcaster account), verified via Quick Auth on the mini app; standalone-web users without an FID get packs only (or connect Farcaster to unlock the daily). Confirm this gating lives off-chain (signed mint allowance) rather than on-chain identity.
4. **Hunger → jackpot gating** requires `Jackpot.sol` to read feed state from `Staking.sol` at resolution time — add that interface.
5. **Supply cadence:** daily mints draw from the same global per-letter caps (Appendix A of v0.1). Model mint-out timing once daily-active estimates exist; if mint-out inside ~6 months looks likely, revisit cap multiple (2.5×) before mainnet — flagged, not blocking.

## 6. Unchanged from v0.1 (reaffirming so nothing drifts)

Canonical 4,438-word dictionary as the only claimable set · demand-mirrored letter mint odds (Appendix A) · commit-reveal for all randomness · failed rolls never burn/downgrade (hard compliance rule) · claim escrow of exactly 5 letters, uniform case required to initiate a claim · permanent claims with voluntary dissolution · trophy variants for past answers · LHAW answer hash-chain as a Phase 3 hard dependency · fee split table (v0.1 §6) including 100% snack burn · rarity tiers and stake weights (Appendix B) · phased roadmap order (Mint & Claim → Roll & Shine → Stake & Snack → Deepen), with Showcase slotting into Phase 2 alongside rolls.

## 7. Updated open questions

- Born-shiny cosmetic (1–2% of mints get a permanent cosmetic mark that survives upgrade): **deferred, P2.** Do not build; do not preclude (a per-token cosmetic flag in mint metadata is enough headroom).
- Pricing for daily mint vs. pack vs. roll vs. claim vs. snack: still owed by the Phase 0 tokenomics sim. Daily mint should be priced low enough to be habit, high enough to gate spam — sim will set it.
- Showcase string length cap (currently 8) and whether showcases later become mintable mementos (fee → burn): parking lot, do not design for now.
